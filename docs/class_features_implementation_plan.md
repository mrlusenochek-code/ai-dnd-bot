# Class Features Implementation Plan

Статусы:

- `safe_to_implement_now` — можно внедрять на текущей архитектуре без отдельной системы заклинаний/подклассов.
- `needs_spell_system` — упирается в слоты, подготовку, known/prepared, spell effects или spell-resource economy.
- `needs_subclass_system` — базовая feature есть, но реальная полезность зависит от выбранного подкласса.
- `not_implemented` — feature есть в catalog, но для неё пока нет runtime/mechanics и её рано активировать без соседней инфраструктуры.

## Recommended global order

1. Fighter: `action_surge`, `indomitable`, passive `extra_attack` hook.
2. Rogue: `cunning_action`, `sneak_attack`, `uncanny_dodge`, `evasion`.
3. Paladin: `lay_on_hands`, `divine_sense`, then only later `divine_smite`.
4. Bard: `bardic_inspiration`, `font_of_inspiration`, `song_of_rest`.
5. Barbarian: `rage`, `reckless_attack`, `danger_sense`.
6. Monk: only after introducing a generic per-rest/per-turn resource runtime for `ki`.
7. Artificer utility features and `flash_of_genius`.
8. Full spellcasting classes and spell-driven features after a dedicated spell system.

## Immediate architectural follow-ups

- Reuse `app/rules/class_feature_runtime.py` for all class-feature `mechanics` lookup and class runtime storage.
- Extend `app/web/ws_class_features.py` as the narrow combat router for class actions instead of growing `ws_handlers.py`.
- Add a shared resource model for `per_short_or_long_rest`, `per_long_rest`, proficiency-based uses, and spendable pools (`ki`, `sorcery_points`, `channel_divinity`, bardic dice).
- After that, move other deterministic class actions into the same path: `action_surge`, `indomitable`, `lay_on_hands`, `bardic_inspiration`, `cunning_action`.
